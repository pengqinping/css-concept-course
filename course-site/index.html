CSS 概念课 · 01 / 12

01 · 从规则到像素

一句话模型：浏览器先把 HTML 和 CSS 各解析成 DOM 与 CSSOM，再让它们依次经过样式计算 → 布局 → 绘制 → 合成四道加工；每一道只回答一个问题，DevTools 的面板正好各看其中一道。

先看一个现象

同一条规则，在 DevTools 的四个面板里看到的东西完全不同：

css
.card { width: 50%; transform: translateX(20px); color: #16794a; }
  • Styles 面板：列出命中 .card 的所有规则，width: 50% 旁边可能还躺着被划掉的声明。
  • Computed 面板：width 变成具体的 320px，color 变成 rgb(22, 121, 74)。
  • Layout 面板：显示一个 320px 宽、带明确位置的盒子。
  • Rendering 面板：打开图层边框后，.card 可能自己框出一层。

你以为这四个面板是"同一份样式的四种排版"，实际它们拍的是同一条声明在四个不同加工阶段的快照。看到 50% 还是 320px，取决于你站在流水线的哪一格。

再看一组更别扭的对比：给元素加 transform: translateX(20px)，控制台里 getBoundingClientRect().left 跟着变大，画面也确实移动了；换成改 color，rect 一个数字都不变，画面却也变了。同样是"改了 CSS"，有的动了几何，有的只动外观，有的看着像只挪了画面。浏览器为这三种改动走的路根本不是一条：

css
.box { width: 200px; }                    /* 动几何：rect 变，画面变 */
.box { color: red; }                      /* 动外观：rect 不变，画面变 */
.box { transform: translateX(20px); }     /* 动图层：rect 变，但内容无需重画 */

先建立直觉

图里那条虚线是本篇最容易踩坑的地方，先在脑子里留个位置，结尾"容易误判的地方"会展开它到底成不成立。

机制拆成四步

1. 样式计算：每个元素的每个属性，最终值是什么

输入是 DOM（元素组成的树）和 CSSOM（规则组成的树）。浏览器把它们匹配起来，对每个元素的每个属性跑一遍层叠（上一课的主题），选出胜出的声明得到指定值，再处理继承、单位换算和百分比解析，得到计算值。

为什么 width: 50% 在这里变成 320px？因为百分比本身不是长度，必须乘一个参照宽度才落地——这个参照盒由包含块规则决定（第 05 篇）。Computed 面板显示的就是这一步的结果，所以它总是带单位的具体值，不会是百分比。Styles 面板显示的则是"你写下的字面量 + 哪些规则命中 + 哪些被划掉"，两者看的是同一属性的不同阶段。

同理，font-size: 1.5em 在不同父元素下会算出不同像素；color: currentColor 要等继承链确定后才知道自己是什么颜色。这些换算和求解都发生在样式计算，而不是等到绘制才补。等走到布局时，每个属性的值都已经是一份没有歧义的数字或关键字。

值的推进是一条短链：声明 width: 50% 经层叠胜出后成为指定值 width: 50%，再经百分比解析成为计算值 width: 320px。Computed 面板停在最末一格，所以你在那里永远看不到 50%。

这一步回答的问题：用哪个值。

2. 布局：每个盒子在哪里、多大

样式计算知道了"多宽"，布局要回答"放在哪"。浏览器按正常流、flex、grid 等规则，把计算值换算成实际几何：位置坐标、宽高、外边距是否折叠、文本换行后的真实高度。

为什么这一步必须单独存在？因为一个元素的尺寸和位置常常取决于兄弟和父级——flex 分配剩余空间、垂直 margin 折叠、文字换行撑高容器，都得等所有相关元素凑齐才能结算。布局是一次"全局结算"，没法边读 CSS 边算。

一个具体例子：上下相邻的两个块，上面的 margin-bottom: 30px、下面的 margin-top: 20px，最终间距是 30px 而不是 50px——垂直 margin 会折叠，取较大者（第 04 篇）。这个结论只有把两个盒子摆在一起才得得出，单独结算其中任何一个都算不出来。这解释了为什么布局不能"边解析边出图"。

getBoundingClientRect() 读的就是布局结果。改 width、font-size、增删 DOM 节点都会推翻重算，这就是常说的重排（reflow）。

这一步回答的问题：放哪里、占多大。

3. 绘制：按什么顺序画、画什么

布局定下几何，但还没决定一个像素的颜色。绘制阶段把每个盒子拆成一串绘制指令：先画背景，再画边框，画文字，画阴影……并按层叠顺序排好队（谁在下、谁盖住谁，见第 07 篇）。

为什么布局要和绘制分开？因为很多改动只影响"怎么画"、不影响"在哪"。把 color 从黑改红，盒子位置尺寸分毫不动，没必要重算布局，只需重新发出绘制指令。所以改颜色会跳过布局，但仍要走绘制。box-shadow、border-radius、background 这类属性也落在这一步。

注意绘制指令不是像素本身，而是"在这个矩形填这个颜色、在这条基线画这段文字"这样的配方。把配方变成真正的像素网格叫光栅化，通常也在这一步完成。所以改颜色虽然不用重排，仍然要把那一块重新光栅化一遍——这就是"跳过布局不等于免费"。

这一步回答的问题：画什么、谁盖谁。

4. 合成：把图层叠成一张图

浏览器把画面切成若干图层（layer），分别光栅化成纹理，再由合成线程按层叠顺序拼成最终图像交给屏幕。合成由 GPU 承担，是四步里最便宜的一步。

为什么要有图层？因为分层之后，某些层可以独立地平移、缩放、改变透明度，而不碰其他层的内容——这正是虚线的物理基础。让一个元素"自己成层"，常见手段是给它运行中的 transform/opacity 动画、position: fixed，或 will-change。

合成线程独立于主线程：主线程正忙着布局、绘制时，合成线程仍能把已经做好的图层平滑位移。这是虚线能绕过后两步的物理条件，也是 transform/opacity 动画在主线程繁忙时往往依然流畅的原因。

但图层不是越多越好：每层都要占一份显存，层数过多反而拖慢合成。浏览器只在确有需要时提升图层，不会因为写了 transform 就无条件给每个元素单开一层。

这一步回答的问题：各层怎么叠成最终画面。

把面板和阶段对上号

现在可以回答开头的疑问了。四个面板不是四种"样式视图"，而是四个阶段的观察窗：

面板你看到的东西所处阶段为什么停在这一格
Styles命中的规则、字面量、被划掉的声明样式计算的输入展示的是候选声明，层叠还没跑完
Computed每个属性的最终值（320px、rgb(...)）样式计算的输出百分比、em 已换算，继承值已填入

Rendering闪烁的绘制区域、图层边界绘制 + 合成这两步的结果不是属性，只能用可视化标出

为什么没有专门的"绘制"面板？ 因为绘制的产物是一串指令而不是属性值，没法像 width 那样列出来。Rendering 面板用 Paint flashing（哪里重画就闪绿）和 Layer borders（哪块自成一层）把这条看不见的流水线，翻译成人眼能看见的信号。

容易误判的地方

  • "改了样式就一定重新布局" → 不一定。只改颜色、阴影这类"怎么画"的属性，布局结果没变，浏览器跳过布局直接绘制。getBoundingClientRect() 在改颜色前后返回同样的盒子。
  • transform/opacity 动画"永远不重绘" → 只对"已提升为独立图层、且只是平移/旋转/整体透明度变化、内容无需重新光栅化"的情形成立。一旦 scale 放大到超出原纹理分辨率、元素带 filter 或混合模式、或元素压根没被单独分层，浏览器仍会重新绘制。准确说法是：这些属性给了浏览器"只走合成"的机会，不是保证。
  • "Computed 等于我写的 CSS" → Computed 是样式计算后的结果：red 变 rgb(255, 0, 0)、50% 变具体像素、继承来的值也出现在这里。它是"浏览器实际用的值"，不是你写下的字面量。

把四步和四个面板连起来记：Styles 看输入、Computed 看输出、Layout 看几何、Rendering 看绘制与合成。下面三道题分别卡在这条链的不同位置。

02 · 谁说了算

一句话模型：层叠不是"后写的覆盖先写的"，而是一串有先后的关卡——先比来源与重要性，再比层，再比优先级和作用域距离，最后才轮到书写顺序。

先看一个现象

下面两条规则都命中同一个按钮。按"后写覆盖前写"，按钮应该是蓝色：

css
.button { color: red; }
.button { color: blue; }

但如果第一条写在一个 layer 里，第二条写在另一个 layer 里，结果可能反过来：

css
@layer base, overrides;

@layer base {
  .button { color: red; }
}
@layer overrides {
  .button { color: blue; }
}

这时蓝色赢，是因为 overrides 层排在后面——即使 base 里的选择器写成 .button.button.button（优先级更高）也赢不了。层比优先级更早被比较。

再换个情况：如果红色那条加了 !important，蓝色就输了；而如果蓝色写在未分层的样式里且带 !important，又会重新赢回来。这些"反直觉"的结果，都是因为比较顺序在起作用。

先建立直觉

图里最关键的一条：重要性会反转层的顺序。普通声明是"后层强"，重要声明变成"先层强"。

机制拆成五步

1. 先筛：哪些声明有资格参赛

选择器必须命中这个元素，媒体查询/容器查询的条件必须成立。没命中的规则根本不进入比较。

这一步常被忽略：你以为在跟某条规则竞争，其实那条规则的 @media 条件没成立。

2. 比来源与重要性

先分出"谁家的声明"，再分有没有 !important。从低到高的顺序是：

顺序来源说明
低用户代理普通声明浏览器默认样式
↓用户普通声明读者自己的浏览器设置
↓作者普通声明你写的 CSS
↓CSS 动画@keyframes 运行中的值
↓作者 !important见下方警告
↓用户 !important用户无障碍设置在此
↓用户代理 !important极少数浏览器强制样式
高CSS 过渡正在 transition 的属性值最高

为什么这样排？ 动画要盖过普通样式才能动起来，所以高于普通作者声明；但用户用 !important 表达的辅助需求（比如强制高对比度文字色）要盖过动画，所以用户重要声明在动画之上；过渡是用户对"当前这帧"的即时期望，所以最高。

由此得到一个实用结论：不要用 !important 去盖用户的无障碍设置，你盖不住，而且会破坏别人的阅读体验。

3. 比层（@layer）

同一来源、同一重要性下，先比较层：

  • 普通声明：先声明的层弱，后声明的层强；未分层样式强于所有分层样式；行内 style 又强于未分层样式。
  • 重要声明：顺序反转——先声明的层强，后声明的层弱，未分层最弱。
css
@layer reset, base, components;

/* 普通声明：components 最强，reset 最弱 */
/* 重要声明：reset 最强，components 最弱 */

为什么要有层？ 它把"谁应该覆盖谁"从选择器优先级里抽出来，变成一句显式的顺序声明。写 @layer reset, base, components 的意思就是：重置规则无论选择器多宽泛都不该压过组件样式，不用靠 !important 或堆叠类名来实现。

4. 比优先级与作用域距离

前面都打平，才轮到选择器。优先级按四元组记：

text
(行内, ID, 类/属性/伪类, 标签/伪元素)

.button 是 (0,0,1,0)，#app .button 是 (0,1,1,0)，style="..." 是 (1,0,0,0)。逐位比较，前一位大就赢，后面的位不再看。

*、>、+ 这些组合器不贡献优先级；:where() 整个括号贡献 0，:is() 取参数中最高的一项。!important 不参与优先级计数，它属于第 2 步。

如果优先级也相同、且用了 @scope，则离 scope 根更近的胜出（跨越的 DOM 层级更少）。这是最后一步之外的补充判定，只在 scoped 规则之间发生。

5. 最后才比书写顺序

只有来源、重要性、层、优先级、作用域距离全部相同，后写的才赢。

css
p { color: red; }
p { color: blue; }   /* 蓝色赢：前面全部打平 */

记住这个顺序后，判断风格冲突就有了固定动作：先看来源和 !important → 再看有没有层 → 再看选择器 → 最后才数行数。

03 · 值从哪里来

一句话模型：一个属性的值先由级联选出胜者；没选中就顺着继承链找父级；父级也没有就用初始值——继承 / 初始值 / 级联结果，是指定值仅有的三个来源，五个全局关键字只是强行改道。

先看一个现象

css
.parent { color: #16794a; border: 2px solid #b8860b; }

给 .parent 里放一个空的 <span>，你以为子元素"什么都没写就什么都没有"，实际它显示绿字，边框却一点没有。color 顺着父子链传下来了，border 没有。

更反直觉的是关键字：

css
.child-a { color: unset; }   /* 绿色 */
.child-b { border: unset; }  /* none */

同一个 unset，一个表现得像继承、一个表现得像初始值。你以为关键字有固定含义，实际它的含义取决于被用在什么属性上。

先建立直觉

记住这句话就能推演大部分结果：先看级联有没有选中，再看这个属性继不继承，最后才是初始值。

机制拆成四步

1. 指定值只有三个来源

浏览器把"这个属性现在该用什么值"叫指定值。它的来源按顺序只有三个：

  1. 级联结果：上一课跑完层叠，有声明胜出，就直接用它。
  2. 继承：没有胜出声明，且属性是继承的，取父元素的计算值（不是父元素写下的字面量）。
  3. 初始值：前两个都不成立，取规范为这个属性定义的初始值。

为什么第 2 步取"计算值"而不是父元素写的字？因为父元素可能写了 font-size: 1.2em，子元素继承到的是已经换算好的像素值。继承传递的是结算完的结果，不是原始配方。

哪些属性继承？用一个标准判断：这个属性如果全家不一致会不会很怪。文字颜色、字体、字号、行高、对齐方式、列表样式——一家人应该一致，所以继承。宽度、内外边距、边框、背景、定位、盒模型——如果也继承，每个子元素都会复制父元素的盒子，显然荒唐，所以不继承。

这一步回答的问题：没写声明时，默认去哪取值。

2. 五个全局关键字是改道开关

每个 CSS 属性都能用这五个关键字，它们强迫浏览器走指定路线：

关键字走哪条路什么时候用
inherit强制走继承，取父元素计算值给不继承的属性强行统一，如 border-color: inherit
initial强制走初始值把属性清回规范默认值
unset继承属性走 inherit，非继承属性走 initial想"恢复天然状态"，不管它继不继承
revert回滚到更低来源（用户样式或浏览器默认样式）撤销自己写的样式，露出浏览器默认
revert-layer回滚到上一个 @layer；没有上层则等同 revert在分层体系里只撤销本层的覆盖

unset 为什么因属性而异？ 因为它被定义成"继承属性就继承，不继承就初始"——正是默认来源链的快捷方式。所以 color: unset 拿到父级绿色，border: unset 拿到初始值 none。它不是"清空"，而是"回到没写过声明时的样子"。

initial 和 revert 最容易混。 初始值来自规范，浏览器默认样式来自 UA 样式表（浏览器的内置规则），两者不是一回事。链接是绝佳例子：

css
a { color: initial; }   /* 黑色：color 的初始值是 canvastext */
a { color: revert; }    /* 蓝色：露出 UA 样式给链接的默认色 */

revert-layer 与 revert 的差别是"退几格"。 revert 退到上一个来源（作者 → 用户 → UA），revert-layer 只在 @layer 的栈里退一层；没有更低的层可退时，它的行为就退回 revert。

这一步回答的问题：怎么强制改变取值路线。

3. 自定义属性是继承的 token

自定义属性（以 -- 开头）有两件事必须先说清：它们默认继承，而且存的是 token 序列（一串还没解析的字符），不是解析好的值。浏览器读到 --size: 20px 时不会校验它是不是长度，只把 20px 当字符存着；直到 var(--size) 被替换进某个属性，才按那个属性去解析。

为什么这么设计？因为它让自定义属性几乎什么都能存——颜色、长度，甚至一整段 1px solid red。代价是浏览器不知道它的类型（下一步补上这一点）。

var() 的第二个参数是回退值，但回退只在变量没定义时生效：

css
.box { --size: 20; width: var(--size, 100px); }

这里 width 不是 100px。因为 --size 已经定义了，回退不触发；但 20 不是合法长度，声明在计算值时变成"值无效"（IACVT，computed-value time 无效），width 于是表现得像被设成 unset——width 不继承，所以取初始值 auto。

这就是"无效值"语义：回退救不了"定义了但值不对"，只能救"压根没定义"。 想让回退生效，得让变量处于未定义状态，比如把 --size 那行整个删掉。

还有个边角：变量被赋成空值 --size: ; 也算"已定义"（存的是空 token 序列），回退同样不触发，结果仍是 IACVT。

这一步回答的问题：变量里的值什么时候算数、什么时候不算。

4. @property 让变量可以插值

自定义属性默认是 token 序列，浏览器不知道 --angle 是个角度，所以给它做过渡动画时只能从起点直接跳到终点，没有中间帧。注册一下就好了：

css
@property --angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}

注册给变量补上了类型，浏览器于是知道怎么在 10deg 和 90deg 之间插值，动画才平滑。注册时还必须显式写 inherits（不再享有"默认继承"），并给出与 syntax 匹配的 initial-value；像 <angle> 这样的语法必须给初始值。

@property 在这里只解决一件事：让变量从"一串字符"变成"有类型的值"，从而可插值。 别的多态用途不在此展开。

这一步回答的问题：为什么变量动画不能插值，怎么才能插值。

04 · 元素到底占多大

一句话模型：一个盒子由 content / padding / border / margin 四层叠成；box-sizing 不改变任何尺寸，只改变 width 描述的是哪一层——content-box 描述内容层，border-box 描述"内容 + 内边距 + 边框"那一层。

先看一个现象

css
.box {
  width: 300px;
  padding: 20px;
  border: 5px solid #b8860b;
}

你以为拿尺子量是 300px，实际是 350px——padding 和 border 各自左右各来一份，悄悄加了 40 + 10 = 50px。

改成 box-sizing: border-box 再量，变成了 300px。但这时真正放内容的地盘只剩 250px。你以为少的是边角，实际少的是整块内容宽度。

再加上 margin: 20px，横向总占空间分别是 390px 和 340px——margin 又加了 40px，但这次它不属于盒子自身。

还有一种更隐蔽的溢出：三列等宽的 flex 容器里，只要某一列塞进一长串不换行的文字，它就不会等宽，而是把整个容器撑出去。这跟 padding/border 无关，是另一个默认在作怪（第 4 步会揭晓）。

先建立直觉

一句话抓住这张图：box-sizing 换的不是盒子，是尺子的起点。

机制拆成四步

1. 四层各管什么，margin 为什么在盒外

从里到外：

  • content：装文字和子元素的地方，width/height 默认描述它。
  • padding：内容与边框之间的缓冲，会被背景填充，透明但占位。
  • border：边框本身，占据实实在在的宽度。
  • margin：盒子之外的透明间距，不填充背景、不能放内容，作用是"我和别人之间留多远"。

为什么 margin 必须在盒外？因为它表达的是关系而不是自身：两块内容之间的呼吸，属于它们之间的空隙，不属于任何一块。把它算进盒子，就等于把"关系"塞进了"物体"，布局和折叠都会乱套（第 3 步会看到后果）。

所以 width 再怎么算，都只在前三层里打转；margin 另算。

一个验证技巧：默认 background-clip: border-box，背景会铺到边框外沿，但绝不会铺进 margin。打开背景色就能一眼看出盒子到哪为止、哪一段是 margin。

2. box-sizing 换的是 width 描述哪一层

固定用开头那组数字：width: 300px; padding: 20px; border: 5px（左右各一份），两种模式放在一起对照：

量的是什么content-box（默认）border-box
width: 300px 描述的是内容层 = 300px内容 + padding + border = 300px
内容实际宽300px300 - 2×20 - 2×5 = 250px
盒子实际占位（不含 margin）300 + 40 + 10 = 350px300px
加上左右 margin: 20px 后350 + 40 = 390px300 + 40 = 340px

数字是同一组，只有 300px 标在哪一层变了。这就是为什么两种模式看起来"换数字"——其实换的是参考点。

为什么要有两种？content-box 是历史默认，padding 和 border 会在你声明的宽度上"额外加价"，算栅格时容易溢出；border-box 让"我声明多宽就占多宽"，把 padding 和 border 从外面挪到里面消化，更适合按列算尺寸。所以很多项目会把 *, *::before, *::after { box-sizing: border-box } 设为全局默认。

注意 border-box 不是"内容宽也是 300px"——恰恰相反，内容宽被 padding 和 border 吃掉了。

3. 垂直 margin 折叠：相邻兄弟取较大值

看两个上下相邻的块：

css
.a { margin-bottom: 30px; }
.b { margin-top: 20px; }

它们的间距是 30px，不是 50px——两个垂直 margin 相遇时会折叠成一个，取较大的那个。max(30, 20) = 30。

为什么会折叠？因为垂直 margin 表达的是"两段内容之间要呼吸"，两个相邻的呼吸叠在一起会浪费空间。浏览器把它理解成"这一段间距至少要有多少"，于是取最大值而不是相加。这正好呼应第 1 步：margin 是关系，不是实体，所以它可以重叠。

边界要说清：折叠只发生在垂直方向、正常流的块级盒之间。水平 margin 从不折叠；flex 或 grid 子项之间的 margin 也不折叠——它们各有各的布局规则。父子之间的垂直 margin 也会折叠，那是第 06 篇"格式化上下文"要处理的事。

4. min-width: auto 让 flex/grid 子项撑破容器

普通块级元素的 min-width 初始值是 auto，但浏览器把它当 0 用——所以你能把块压到很窄。flex 和 grid 的子项不一样：它们的 auto 会解析成基于内容的最小尺寸，也就是内容再挤也不能小于的宽度（比如一个不换行的长单词、一张固定宽的图片）。

css
.row  { display: flex; width: 300px; }
.item { flex: 1; }  /* 内容是一串不换行的长文本 */

你以为三项均分，实际长文本那项把容器撑破了，出现横向溢出。原因是 min-width: auto 挡住了收缩：flex: 1 想把它压到 100px，内容说"我最少要 200px"，auto 选了后者。

为什么浏览器默认这样？因为把内容压到看不清比溢出更糟——这是保护性默认。要让它按你的意愿收缩，得显式解除保护：

css
.item { flex: 1; min-width: 0; }

min-width: 0 把"内容最小尺寸"改成 0，子项就能真正均分了；代价是内容可能被截断或溢出，需要配合 overflow 或省略号处理。

grid 子项踩的是同一个坑：grid-template-columns: repeat(3, 1fr) 遇到长内容时，那一列会突破 1fr 的均分。解法写成 repeat(3, minmax(0, 1fr))，本质也是把最小尺寸从 auto 改成 0。

05 · 百分比是谁的百分比

一句话模型：width: 50% 里的 50% 不是一个长度，而是一个待解析的比例。解析之前必须先确定"参照盒"（包含块）；定位方式一变，参照盒就换，结果自然不同。

>

包含块不是某个元素的别名，而是浏览器为这个子元素临时划定的一块矩形画布。

先看一个现象

同一个父元素、同一个子元素，只改一句 position：

html
<div class="box">
  <div class="child"></div>
</div>
css
.box {
  width: 400px;          /* 假设 box-sizing 为默认的 content-box */
  padding: 20px;
  border: 2px solid #888;
}
.child {
  width: 50%;
  height: 40px;
}
/* 情形 A：.child 是普通流子元素 */
/* 情形 B：.box { position: relative } 且 .child { position: absolute } */

情形 A 里 .child 宽 200px，情形 B 里同样一句 width: 50% 变成 220px。

你以为：50% 就是"父元素宽度的一半"，写多少就是多少。 实际：父元素的 content box 宽 400px，padding box 宽 440px（400 + 20×2）。一半到底是 200 还是 220，取决于浏览器拿哪个盒子当参照。父元素的 border 那 2px 在这里完全不参与——它已经站在参照盒的外面了。

用开发者工具量一下会发现更刺眼的细节：情形 B 里子元素的左边缘从父元素的 padding 外沿开始，紧贴着内边距的右侧；而情形 A 里子元素的左边缘从 content box 左边缘开始，被 20px padding 推开。也就是说，换 position 同时换掉了两件事：量百分比的尺子和摆放子元素的原点。它们来自同一个包含块，所以必须放在一起理解。

先建立直觉

图里要看出一件事：百分比本身没变，变的是尺子的起点和终点。 与其死记"绝对定位 padding box"，不如养成习惯：看到百分比，先问"这把尺子搭在哪个盒子上"。

读图可以按三个动作走：先看子元素在不在正常流里，再沿 DOM 往上找它的参照盒，最后才把百分比乘上去。三步里最常被跳过的是第二步，而它恰恰是唯一决定数值的一步。用开发者工具悬停 .box 时，盒子模型高亮会把 content、padding、border 三层分别标色：情形 A 命中中间那层，情形 B 命中外面那层。

机制拆成四步

1. 百分比必须先找到一个参照盒

百分比是相对值，而布局最终要的是绝对长度。浏览器必须在布局阶段把 50% 解析成一个具体的 px 数才能画盒子，这个被拿来乘的数字就来自包含块（containing block）。

为什么不能"先放着"？ 因为盒子尺寸、位置、换行都依赖这个数，多个属性会连锁引用它；没有确定的参照，整条布局链都算不下去。所以规范不写"百分比大概是多少"，而是为每种定位方式明确规定一个包含块。

注意解析是一次性的：浏览器不会等兄弟元素排完再回头改比例。包含块一旦定下，50% 就立刻被锁成一个 px 值，后续布局只认这个结果。这也是为什么"事后把父元素改宽一点"能让子元素跟着变——那其实是重新做了一次解析。

2. 普通流子元素：参照父元素的 content box

正常流里的块级子元素，排在父元素的内容区里。它的包含块就是父元素的 content box，所以 width: 50% = 400 × 50% = 200px。

为什么是 content box 而不是别的？ 父元素的 padding 是父元素自己的留白，不是子元素可以占用的地盘；子元素从内容区左上角开始排，自然以内容区为坐标系。

这里有个容易绕晕的细节：本例父元素是默认的 box-sizing: content-box，width: 400px 描述的就是 content box，所以加 padding 并不会把它从 400 挤小，只会把外层的 padding box 撑到 440。只有当父元素写成 box-sizing: border-box 时，width: 400px 才描述边框外沿，padding 增加才会反过来压缩 content box，普通流子元素的 50% 才会跟着变小。两种情况下"加 padding → 子元素变窄/不变"的差别，根源都在参照盒是谁。

3. 绝对定位子元素：参照最近定位祖先的 padding box

绝对定位元素脱离了正常流，它不再待在父元素的内容区里，而是找一个"愿意当坐标系"的祖先：最近的 position 不为 static 的祖先。它的包含块是这个祖先的 padding box——注意是 padding box，不是 content box，也不是 border box。

于是例子里的算式变成：(400 + 20×2) × 50% = 440 × 50% = 220px。border 的 2×2px 不属于 padding box，所以既不进算式，也不决定子元素的起点。

为什么只写 position: relative、一个 top/left 都不给也够了？ 包含块的认定只看 position 的值，不看祖先是否真的移动过。祖先原地不动，但它的 padding box 已经悄悄成了子元素的坐标系——这是"定位祖先"这个称呼里最容易被误读的地方。

为什么是 padding box？ 绝对定位的原点在祖先内边距的外沿（padding edge），padding 因此被收进了它的画布。你可以把它理解为：一旦脱离正常流，子元素就从"内容区里的居民"变成"贴着祖先内壁作画的人"，内壁就是 padding 的外边界。

同一把尺子也管偏移：left: 10% 参照 padding box 的宽度，top: 10% 参照它的高度。为什么两个方向用同一个盒子的不同维度？ 包含块就是一个矩形，宽高各取一次即可；这里没有"top 参照宽度"之类的特殊规则，那种例外出现在百分比 padding / margin 上（它们一律参照包含块宽度），不要混进来。

如果一路往上都没有定位祖先，包含块退化为初始包含块：一个尺寸等于视口、锚在文档原点的矩形。这时 width: 50% 就是视口宽度的一半；页面滚动时它不会跟着文档内容移动。

4. fixed 参照视口，但有一道暗门

position: fixed 的包含块是视口，所以它不随滚动移动，50% 就是视口宽度的一半。

为什么是视口？ fixed 的语义就是"钉在屏幕上"，当然要用屏幕这块画布做参照。

暗门在于：如果某个祖先带有非 none 的 transform、filter、perspective，或 contain: paint/layout 等属性，它会悄悄变成 fixed 后代的包含块。这时 fixed 突然开始跟着那个祖先走，50% 也不再是视口的一半——很多"fixed 失效了"的怪事都出自这里。

为什么要留这扇暗门？ 因为 transform 会创建新的绘制上下文，元素内部的坐标必须相对于变换后的祖先来解释；如果还按视口算，transform 一移动，fixed 子元素就会错位。规范的取舍是：宁可让包含块换人，也要保证变换后的整体是自洽的。

06 · 为什么布局会塌

一句话模型：BFC（块格式化上下文）不是一串触发条件，而是一道边界——它把盒内的竖直 margin 折叠和浮动的影响关在里面，不让它们穿出去改写外面的布局。

>

判断时只问一句：这道边界在不在？不在，内部影响就会往外漏。

先看一个现象

先是最常见的一种"塌"：

html
<div class="parent"><p class="child">一段文字</p></div>
css
.parent { background: #e8e3d5; }
.child  { margin-top: 50px; }

你以为：子元素与父元素上边缘之间出现 50px 空隙，父元素的米色背景从空隙上方开始。 实际：父元素整体被往下推了 50px，背景的上边缘也跟着下移；父子之间反而没有空隙。

第二种"塌"同样典型：父元素里只放浮动子元素，不给高度。父元素的高度算成 0，背景和边框缩成一条线，浮动的卡片溢出到下面的内容上。

两个现象看起来无关，其实是同一件事：父元素没有形成一道挡住内部影响的边界。margin 穿了出去，浮动也跑了出去。

用开发者工具选中父元素，盒子模型高亮会给出线索：第一种情况里 50px 落在父元素的外边距区域；第二种情况里父元素的高度直接显示 0。先看到"影响跑到了哪里"，再去找"为什么没有边界"，顺序不要反。

先建立直觉

看图时不要去数"这里有几个属性"，只盯住那条边界：边界之内的 margin 和浮动不能越过它，边界之外的也不能进来。 剩下的规则都是从这一句推出来的。

机制拆成四步

1. 竖直 margin 为什么会"穿透"

正常流中，上下相邻的 margin 会折叠：两个 50px 不会叠成 100px，而是合并成一个 50px。父子之间也适用这条规则——如果父元素的上边缘和第一个正常流子元素的上边缘之间，没有 border、没有 padding、也没有行内内容，它们二者的上 margin 就折叠，并且折叠后的 margin 被放在父元素外面。

所以例子里父元素没有 margin-top，子元素写了 50px，结果不是"子元素在父元素里往下 50px"，而是"这一对盒子整体往下 50px"。所谓穿透，其实是折叠的结果落在了外面。同样的事也发生在底部：最后一个子元素的下 margin 会与父元素的下 margin 折叠，把父元素的底边往下带。

为什么只在竖直方向？ 水平 margin 从不折叠，这是块布局的既定规则；竖直方向折叠的原始意图是让相邻段落自然取较大的间距，而不是把两个段落的间距相加。理解意图比背结论有用：你看到"该有空隙的地方没有空隙"，先怀疑折叠，再看有没有边界。

2. 边界一立，折叠就停在门口

成为 BFC 的元素，它的 margin 不会与内部正常流子元素的 margin 折叠。折叠关系跨不过这道边界，于是子元素的 50px 只能老老实实待在父元素里面，把内容往下推，父元素本身不动。

为什么 BFC 能阻断？ BFC 是一块独立的布局区域。浏览器计算它的尺寸和位置时，把内部当成另一个世界：内部子元素的 margin 只跟内部发生关系，不与外壳的 margin 合并。边界同时是尺寸的隔离层——内部怎么变，外面对它的定位不受影响。

注意 border 和 padding 是另一种阻断方式：它们不是靠"立边界"，而是靠在父子 margin 之间插进一段实体，让两者不再相邻，从而根本不构成折叠条件。两种阻断的机理不同，但都表现为" margin 不再穿透"，别把它们记成同一条规则。

3. 立边界的几种方式，代价不一样

下面每条规则单独建立 BFC。它们不是可以互换的写法，副作用差别很大，选择时看你能接受什么：

css
/* 方式一：flow-root —— 专门为建立边界而生，不改变盒的位置、不裁剪内容 */
.parent { display: flow-root; }
css
/* 方式二：overflow 非 visible —— 顺带裁剪溢出内容，可能出现滚动条 */
.parent { overflow: hidden; }
css
/* 方式三：浮动 —— 父元素自己也脱离正常流，会改变它与兄弟元素的关系 */
.parent { float: left; }
css
/* 方式四：绝对定位 —— 同样脱离正常流，参照最近定位祖先 */
.parent { position: absolute; }
css
/* 方式五：contain: layout —— 同时声明内部布局变化不会外溢，优化重排范围 */
.parent { contain: layout; }

为什么不能把这些值堆进同一条规则？ 因为它们建立边界时附带的副作用完全不同：flow-root 只是关起门来；overflow 会裁剪；float 和 absolute 会把父元素自己从正常流里拿走，连带改变父元素与兄弟元素、与后续内容的关系。混着写，出了问题你就分不清是哪个副作用救了你、又是哪个副作用制造了新问题。

实际取舍很简单：想消除"塌"又不想改变别的，display: flow-root 是首选；如果本来就打算裁剪溢出，overflow: hidden 可以顺手解决；float 和 absolute 只在元素本来就需要脱离文档流时才用。

4. 浮动为什么能被"包住"

父元素只含浮动子元素时高度为 0，是因为浮动脱离了正常流，计算父元素高度时不被计入。让父元素成为 BFC 后，规范要求计算它的高度时把内部的浮动也纳入，于是高度重新长出来，背景和边框把卡片包住。

为什么 BFC 必须包含浮动？ BFC 的基本约定是"内外互不干扰"：边界内的浮动不能溢出到边界外影响后面的盒子，边界外的浮动也不能挤进内部。既然不允许溢出，计算边界尺寸时就必须把这些浮动算进去——包住它们是这条约定的必然结果，不是额外补丁。

这也解释了浮动文字环绕：文字所在的 BFC 不会与旁边的浮动重叠，于是自动让出位置，而不是被浮动的背景盖住。

  • "所有相邻 margin 都会折叠" → 只有正常流中的竖直 margin；被 border/padding 隔开、跨 BFC 边界、或涉及浮动与绝对定位盒时不折叠。
  • "包住浮动还得写 clearfix 空元素" → 那是 BFC 普及前的老办法。让父元素成为 BFC 即可；空元素只是人为造一个能创建边界的盒子，不如 display: flow-root 直接说明意图。

CSS 概念课 · 07 / 12

07 · 谁盖住谁

一句话模型：层叠上下文是一个"家族"。浏览器先比较家族在整个页面里的层级，再比较家族内部的排位；z-index: 9999 只在自己家族里排第一，出了家族没人认。

>

看见 z-index 先别比数字，先问一句：它们俩在同一个家族里吗？

先看一个现象

一个弹层徽标，一个盖住它的遮罩：

html
<div class="a"><span class="badge">9999</span></div>
<div class="b"><span class="cover">0</span></div>
css
.a { position: relative; z-index: 1; }
.b { position: relative; z-index: 2; }
.a .badge { position: absolute; z-index: 9999; }
.b .cover { position: absolute; z-index: 0; }

你以为：9999 是全页面最大的数字，徽标一定浮在最上面。 实际：.cover 盖在 .badge 上面，哪怕它只写了 z-index: 0。

原因不在数字大小，而在比较的层级：.badge 属于 .a 这个家族，.cover 属于 .b 这个家族。浏览器在比较两者之前，先比较了 .a（1）和 .b（2）——家族 A 整体排在家族 B 下面，A 家内部再大的数字也翻不过来。

在开发者工具里逐个元素悬停，会看到 .badge 的 9999 确实生效了：它在 A 家内部排第一。问题从来不是它没生效，而是生效的范围不包括 B 家。

先建立直觉

看图时的关键动作是：先找元素所在的家族，再找家族在整个剖面里的位置，最后才看家族内部的排位。 三步里最容易被跳过的是第二步，而 9999 输掉恰恰就输在第二步。

机制拆成四步

1. z-index 的比较范围只到"同一个家族"

z-index 不是全页面统一排序的号码，它只在同一个层叠上下文内部有效。跨上下文时，先看各自上下文在父上下文里的排位；排在下面的上下文，内部数字再大也会整体被盖住。

为什么不能全页面统一比？ 因为绘制是按树递归进行的。浏览器把每个层叠上下文当成一个整体，在父上下文的某个层级上一次性画完，再画下一层。一旦开始画某个家族，家族内部的成员就已经按序排好了，没有机会"插队"到家族之间。这也是为什么调高子元素的 z-index 常常毫无效果——你动的是家族内部的牌子，而输赢在家族那一层就定了。

家族内部的队列大致是：家族根的背景与边框 → 负 z-index 的子家族 → 正常流块级后代 → 浮动 → 行内内容 → z-index: 0/auto 的定位后代 → 正数 z-index 的子家族。这条队列解释了两个常见困惑：z-index: 0 不是"没层级"，它明确排在正常流之上；负 z-index 也不是消失，只是排在家族内部的靠后位置。

2. 哪些情况会造出一个家族

不必背完整清单，抓住最关键的几种即可，它们的共同点是：让这棵子树成为独立的绘制单元。

  • 定位元素 + z-index 非 auto：最常见。为什么？z-index 需要一个上下文才有意义，浏览器就地造一个给它用。
  • opacity 小于 1：为什么？半透明要求先把整棵子树画好，再整体与背景混合；没有独立单元，混合结果就没法定义。
  • transform 非 none：为什么？变换后的子树要作为一个整体做几何变换，必须先自成一层。transform: translateX(0) 也算数，这是个经典陷阱。
  • isolation: isolate：为什么？它的唯一工作就是明确地说"从这里开始新建一个家族，别受外界混合影响"。
  • flex / grid 的子项设了 z-index（即使 position: static）：为什么？这两种布局允许子项不定位就参与层级排序，于是子项自己成了上下文。

下面三种写法单独出现时，各自都能造出一个家族：

css
.a { opacity: .99; }                 /* 有家族：半透明需要整体混合 */
.a { transform: translateX(0); }     /* 有家族：零位移也算 transform */
.a { isolation: isolate; }           /* 有家族：显式隔离 */

filter、will-change 指定相关属性、contain: paint 也走同一条路：先有独立绘制单元，再有独立层级。 用这条反推，比死记清单可靠。

反过来，z-index 写在 position: static 的普通子项上通常不起作用——牌子要发给家族成员才有意义，Flex/Grid 子项是明确的例外。

3. 根层叠上下文是所有家族的祖宗

文档根元素 html 天然建立根层叠上下文，其他所有层叠上下文都挂在它下面。整页"谁在最上"的最终比较，就发生在根上下文这一层。

为什么必须有根？ 没有最外层容器，绘制顺序就没有起点；浏览器需要一个能把所有家族排成一条队列的地方。这也说明一件事：z-index 的作用域是树状的，同一层能比的只有兄弟上下文，堂兄弟之间要先回到共同祖先那一层比。

为什么强调 html 而不是 body？ body 只是根的一个后代，给它设 z-index 还得先让它定位，那只是又造了一个普通家族，并非根层叠上下文。根只有一个，也不需要你显式创建。

4. 让 9999 真正生效的三条路

既然比较是"先家族、后内部"，解法也只有三种方向：

css
/* 路子一：抬高它所在的家族 */
.a { position: relative; z-index: 3; }   /* 从 1 改成 3，超过 .b 的 2 */

/* 路子二：把徽标挪出低层级家族，例如直接挂到 body 下 */
.badge { position: fixed; z-index: 9999; }

/* 路子三：取消造出家族的属性 */
.a { opacity: 1; transform: none; isolation: auto; }

为什么只有这三条？ 要么让家族升上去，要么换一个家族，要么让家族不复存在——不存在"让子元素越过家族边界"的第四条路，那等于取消边界本身。

路子三有个前提：得先看清家族到底是谁造的。如果 .a 同时有 position: relative 和 z-index: 1，光把 opacity 改回 1 没用，定位加 z-index 这座家族还在；要把 z-index 改回 auto 或去掉定位才算真的拆掉。

注意路子二要小心：徽标移出家族后，它的包含块也会变（见上一篇）。层级问题和参照盒问题经常同时出现，改一处要顺手检查另一处。

08 · 一维空间怎么分

一句话模型：Flex 不是"自动排列"，而是先给每项一个基准尺寸，算出剩余空间，再按系数分配，最后被最小尺寸拦截。

先看一个现象

三张卡片，第一张写 flex: 2，另两张写 flex: 1。你以为宽度是 2:1:1，实际量出来第一张往往没到两倍：

css
.row { display: flex; gap: 16px; width: 600px; }
.row > :first-child { flex: 2; }
.row > :nth-child(n+2) { flex: 1; }

原因藏在 flex 的简写里：flex: 2 展开是 2 1 0%，flex: 1 是 1 1 0%，两者的 basis 都是 0，此时按 2:1:1 分没问题。但如果你写的是 flex-grow: 2，展开后 basis 仍是 auto——每项先按内容占好位置，再分配剩下的空间，结果自然不是 2:1:1。

Flex 的核心不是"对齐"，而是"空间分配"。 对齐只是分配之后的附加动作。

先建立直觉

机制拆成四步

1. 定方向：主轴与交叉轴

flex-direction: row 时主轴是水平方向，column 时主轴是垂直方向。交叉轴永远与主轴垂直。

justify-content 只管主轴，align-items 只管交叉轴——记混了就会调错属性。一个常见误区是给单行 Flex 写 align-content，它只在换行产生多行后才起作用。

2. 定基准：flex-basis

flex-basis 是分配开始前每项在主轴上的尺寸。它优先于 width（row 方向时），auto 表示先看 width，再看内容尺寸。

css
.item { flex: 1 1 100px; }  /* basis = 100px */

flex: 1 等价于 1 1 0%，flex: none 等价于 0 0 auto，flex: auto 等价于 1 1 auto。写简写时把 basis 想清楚，比背口诀有用。

3. 算剩余，按系数分

text
剩余空间 = 容器主轴尺寸 − 所有 basis 之和 − 所有 gap

拿图里的数字走一遍：容器 600px，两项 gap 共 32px，三个 basis 各 100px 共 300px，剩余 600 − 32 − 300 = 268px。grow 为 2:1:1，按四份分：134 / 67 / 67，最终每项 234 / 167 / 167 px。 空间不足时 flex-shrink 按"系数 × basis"加权收缩，不是简单按系数平分——items 基准越大，承担的收缩越多。

4. 被最小尺寸拦截

Flex 子项默认 min-width: auto（column 方向是 min-height: auto），意思是"别比我内容的最小尺寸还窄"。长 URL、长单词会卡在这一步，导致前面的计算全部失效：

css
.row > .url {
  min-width: 0;             /* 允许收缩到内容最小尺寸以下 */
  overflow-wrap: anywhere;  /* 再给文本一个可断行的出路 */
}

为什么不是默认就让它收缩？ 因为默认行为优先保护内容不被裁掉；你需要主动声明"这里允许截断"。

09 · 1fr 到底分到多少

一句话模型：Grid 先画线，再给线之间的轨道定尺寸，最后把项目放进格子；1fr 分的是扣掉固定轨道和 gap 之后的剩余空间，不是"三列就各三分之一"。

先看一个现象

想要三列等宽，写下：

css
.grid { display: grid; grid-template-columns: repeat(3, 1fr); gap: 20px; }
html
<div class="grid">
  <div>短</div>
  <div>短</div>
  <div>Supercalifragilisticexpialidocious</div>
</div>

前两列正常，第三列放了一个不允许换行的长单词 Supercalifragilisticexpialidocious，它突然比另外两列宽了一大截，甚至撑破了容器。

你以为：三个 1fr 就是三等分。实际：第三列的内容把这一列的最小尺寸顶高了，1fr 只能分扣除这个最小值之后的剩余空间。等宽的前提是每列的"下限"相同。

先建立直觉

图里最重要的是第三层：我们平时说的"列"，其实是两条竖线之间的一段轨道。项目不是被"摆"到任意位置，而是被放进由线围出来的格子里。

机制拆成四步

1. 先画线：显式轨道与隐式轨道

grid-template-columns / grid-template-rows 声明的是显式轨道，它们同时定义了网格线的名字和编号。如果一个项目被放到显式网格之外，比如第 5 行，浏览器会自动补出轨道来容纳它，这就是隐式轨道，尺寸由 grid-auto-rows / grid-auto-columns 决定。

为什么先画线？ 因为线是坐标系。没有线，就没有"第几列""跨两列"这些概念；后面所有尺寸计算都是在这套坐标上进行的。

css
.grid {
  display: grid;
  grid-template-columns: 200px 1fr;  /* 两条显式列 */
  grid-auto-rows: 80px;               /* 多出来的行高 80px */
}

给项目设 grid-row: 5 而只声明了 3 行时，浏览器会补出第 4、5 行，它们的高度取 grid-auto-rows 的值（默认 auto，按内容算）。为什么隐式轨道值得单独记住？ 因为你以为"只有三行"时，一个写错的行号会悄悄造出新行，把容器撑高，而你盯着 grid-template-rows 却找不到来源。

2. 再定轨道：fr 分的是剩余空间

计算有严格顺序：

  1. 用容器宽度减去所有固定轨道；
  2. 再减去所有 gap；
  3. 再减去每条轨道的最小尺寸（下一步解释）；
  4. 把剩下的空间按 fr 系数分配。

假设容器宽 900px，grid-template-columns: 200px 1fr 2fr，gap: 20px（两道缝隙共 40px），且各轨道最小尺寸为 0：

  • 剩余 = 900 − 200 − 40 = 660px
  • fr 总数 = 1 + 2 = 3，1fr = 220px
  • 三列分别是 200px、220px、440px（合计 200+220+440+40 = 900px）

写成 CSS 就是：

css
.grid {
  display: grid;
  width: 900px;
  grid-template-columns: 200px 1fr 2fr;
  gap: 20px;
}

为什么先扣固定值和 gap？ 因为它们是确定的，不随剩余空间变化；fr 本质上是一个"占剩余空间几份"的比例，分母必须是被确定项占用之后剩下的部分。所以 1fr 1fr 1fr 只在每列最小尺寸相同时才等于三等分。

3. 最小尺寸：为什么 1fr 会被内容撑开

1fr 的完整含义是 minmax(auto, 1fr)：下限是 auto，也就是该轨道里内容的最小内容尺寸。长单词、不可换行的代码块、固定宽度的图片都会把这个下限顶高，于是轨道无法收缩到按 fr 算出来的值。

把 1fr 换成 minmax(0, 1fr)，就把下限从"内容最小尺寸"改成 0：

css
.grid { grid-template-columns: repeat(3, minmax(0, 1fr)); }

为什么这样有效？ 上限仍是 1fr，分配规则没变；变的只是下限不再被内容抬高。配合 overflow-wrap: anywhere 或让子元素 min-width: 0，长内容就会换行或溢出到轨道内部，而不是把轨道本身撑宽。

4. 最后放项目：命名线与命名区域

grid-template-areas 用名字描述每格属于哪个区域；项目用 grid-area: 名字 对号入座：

css
.grid {
  grid-template-columns: 200px 1fr;
  grid-template-areas:
    "nav  main"
    "foot foot";
}
.item-main { grid-area: main; }

也可以给线起名（[nav-start] 200px [nav-end] 1fr），再用 grid-column: nav-start / nav-end 放置。

为什么用名字？ 列名和区域名把"第几列"换成语义标签，调整列数时不用逐个数线去改 grid-column 的数字。

一句带过：子网格需要跟父级对齐时，subgrid 让子网格直接继承父网格的轨道，而不是自己新建一套线。

10 · 组件自己的断点

一句话模型：媒体查询按视口改页面骨架，容器查询按组件自己所在的空间改内部布局；组件不能只靠视口断点，因为同一个视口能把它放进侧栏、主区或弹窗，而这些位置给它的宽度完全不同。

先看一个现象

一张卡片组件，用 @media (min-width: 800px) 控制"横向排列"：视口大于 800px 时，图片在左、文字在右。

css
.card { display: block; }
@media (min-width: 800px) {
  .card { display: flex; }   /* 横排：图片在左，文字在右 */
}
.sidebar { width: 260px; }
.main    { width: 700px; }

把它放进 1000px 页面的主区，横向排列，很好。再把它放进同页面的 260px 侧栏——视口仍然是 1000px，@media 条件依然成立，卡片还是横排，于是图片和文字挤成一团，文字被压到只剩几十像素。

你以为：写够了视口断点，组件就能适应任何位置。实际：视口只有一个，组件可能被放进很多不同宽度的容器；断点该问的是"我有多宽"，而不是"页面有多宽"。

这张卡片的 CSS 本身没写错，它只是把"视口够宽"当成了"我有足够空间"。这两件事在侧栏里并不等价。

先建立直觉

图的关键：两张卡片代码完全相同，只是所在容器不同，就读出不同的宽度。这正是视口查询做不到的事——它对所有卡片返回同一个数。

读图时按这个顺序：先看 @media 拿到的是哪个数，再看每个 @container 拿到的是哪个数。两者相等时，容器查询没有提供额外信息；只有当容器宽度分化时，它才有用武之地。

机制拆成四步

1. 谁在响应：视口管骨架，容器管内部

页面级的两栏/三栏切换由视口决定，因为那是页面整体的形状；卡片内部的图文排列由容器决定，因为那是组件局部的形状。

为什么组件不能只靠视口断点？ 同一个视口宽度下，组件可能被放进窄侧栏、宽主区、弹窗、网格单元格，可用宽度各不相同。视口断点无法区分这些位置，所以它只能管"整体骨架"，管不了"每个格子里长什么样"。

要回答的问题由谁回答读的数
页面整体分几栏媒体查询 @media视口宽
卡片内部横排还是竖排容器查询 @container离它最近的查询容器宽
卡片字号用哪个参照cqi / cqw 或 vw容器宽或视口宽

三者各管一层，互相不替代。选之前先问"这个决定依赖的是整体还是局部空间"。

2. 建立查询容器：container-type 与它的副作用

要让组件能被查询，先给它的父容器声明 container-type：

css
.slot { container-type: inline-size; }   /* 只按行内方向（通常是宽度）可查询 */
.card { ... }
html
<div class="slot"><div class="card">…</div></div>

副作用必须知道：container-type 会开启对应方向的尺寸包含（size containment）——容器在该方向上的尺寸不再由内容撑开。用 inline-size 时，宽度不再被内容撑开，所以你必须显式给它一个宽度（比如 width: 100% 或网格轨道宽度）；高度仍由内容决定，不受影响。如果写 size，两个方向都被包含，高度也会塌成 0，除非显式指定。

为什么要有这个副作用？ 查询容器若能被自己的内容改变尺寸，就会出现"尺寸影响查询条件、条件又反过来改变内容"的循环。先让尺寸独立于内容，查询结果才稳定、可解析。

3. @container：条件读的是容器尺寸

css
.card { display: block; }
@container (min-width: 420px) {
  .card { display: flex; gap: 16px; }
}

条件成立时，卡片改成横向。这里的 420px 读的是 .slot 的宽度，不是视口。页面上有多个查询容器时，用 container-name 指定查哪一个：

css
.slot { container-type: inline-size; container-name: aside; }
@container aside (min-width: 420px) { ... }

为什么条件要按容器读？ 因为响应的是组件被分配的可用空间；离它最近的可查询祖先，正是分配这块空间的盒子。

查找规则要记准：不带名字时，找最近的查询容器祖先；带名字时，找最近的同名查询容器祖先；都没找到，条件不成立，样式回退到默认分支。它不会跳过中间那个容器去读更外层的宽度。

4. cqw / cqi：以容器为参照的长度

1cqw 等于查询容器宽度的 1%；1cqi 等于查询容器行内轴尺寸的 1%（在横排书写下就是宽度）。它们让组件内部的字体、间距随容器连续缩放，而不是只在断点处跳变。

css
.card-title { font-size: clamp(16px, 4cqi, 24px); }

容器 400px 时 4cqi = 16px，容器 200px 时 4cqi = 8px（会被下限兜到 16px）。回到开头的场景：260px 侧栏里 4cqi ≈ 10.4px，标题被兜到下限 16px；700px 主区里 4cqi = 28px，标题被上限压到 24px——同一个组件，字号自然不同。

为什么需要这类单位？ vw 以视口为参照，同一个组件在不同宽度的容器里会得到相同字号；cqi 以容器为参照，才能做到"侧栏里小、主区里大"。

11 · 单位各以谁为参照

一句话模型：每个 CSS 长度单位都自带一个参照物——rem 看根字号、em 看自身字号、% 看包含块的对应维度、vw 看视口、cqw 看查询容器、ch 看 "0" 的宽度；clamp() 只是把带参照物的值夹在上下限之间。

先看一个现象

想要"每级标题比父级大 1.25 倍"，写：

css
.text { font-size: 1.25em; }
html
<div class="text">一级
  <div class="text">二级
    <div class="text">三级</div>
  </div>
</div>

根字号 16px 时，"二级"已经是 25px，"三级"约 31px——每一层都把上一层的字号再乘 1.25，越嵌越大，最后撑破排版。换成 1.25rem，每一级都稳定在根字号的 1.25 倍（20px）。

你以为：em 和 rem 只是写法不同。实际：em 参照自身 font-size，嵌套时会累乘；rem 永远参照根元素那一个字号，不会累乘。

单位用错时，页面通常不会报错，只会"算出一个你没预期的数"——所以推演参照物比背取值列表更有用。

先建立直觉

这张图要记住的不是公式，而是"先找参照物，再做乘法"。同一个数字配上不同参照物，算出的像素完全不同。

机制拆成四步

1. rem 与 em：根字号 vs 自身字号

rem 取根元素（html）的 font-size；em 取当前元素自身的 font-size。但有一个关键例外：当 em 出现在 font-size 属性上时，它参照的是父元素的 font-size。

为什么有这个例外？ font-size 本身定义了 em 的含义，如果它又参照自身，就成了"用自己定义自己"的循环；参照父级才能打破循环。

设 html 为 16px，父元素 font-size: 1.25em（= 20px）：

  • 子元素 font-size: 1.25em → 20 × 1.25 = 25px（累乘）
  • 子元素 font-size: 1.25rem → 16 × 1.25 = 20px（恒定）
写法参照物嵌套时的表现
1.25rem根字号恒定，不随层级变
font-size: 1.25em父元素字号逐层累乘
padding: 1.25em元素自身字号随自身字号缩放

为什么 rem 更适合全局尺寸？ 它只有一个参照物，不会因为嵌套层级而漂移；em 更适合"跟着本组件字号走"的局部尺寸。

2. %：参照包含块的对应维度

百分比要先解析成像素，参照物就是包含块（见第 05 篇）。width: 50% 参照包含块宽度；top: 10% 参照包含块高度；而 padding 和 margin 的百分比——包括上下方向——都参照包含块的宽度。

css
.box { width: 400px; padding: 10% 5%; }  /* 上下各 40px，左右各 20px */

为什么 padding-top 也参照宽度？ 这样垂直内间距能随宽度一起缩放，保持排版比例；如果参照高度，高度又常由内容决定，会形成循环依赖。

另一个常见的坑：height: 50% 只有在包含块有确定高度时才能解析成像素；父元素高度是 auto 时算不出数，它会被当成 auto 处理。为什么？ 百分比需要一个确定的分母，父高度由内容决定时没有这个分母。

3. 视口、容器与字符单位

  • vw / vh：视口宽/高的 1%，参照物是视口，随窗口缩放；vh 常用于全屏区块的高度，但窗口一变它也跟着变。
  • cqw / cqi：查询容器宽/行内轴尺寸的 1%（第 10 篇）。
  • ch：数字 "0" 在当前字体下的前进宽度，适合按字符数控制行文宽度，比如 max-width: 65ch。
css
.article { max-width: 65ch; }   /* 约容纳 65 个 "0" 的宽度 */

为什么需要 ch？ 它让宽度以"能放下多少字符"为单位，而不是像素；换字体时文本框会自动保持相近的每行字数。注意 ch 取决于当前字体里 "0" 的实际宽度，换字体后同一个 65ch 的像素值会变——这既是它的用处，也是它不适合像素级对齐的原因。

4. clamp：带上下限的插值

clamp(MIN, PREFERRED, MAX) 把首选值限制在上下限之间，数学上等价于：

css
font-size: max(12px, min(4vw, 24px));  /* 等价于 clamp(12px, 4vw, 24px) */

也就是"先取 PREFERRED 和 MAX 中较小的，再取它和 MIN 中较大的"。假设 MIN=12px、MAX=24px：

  • 视口 300px：4vw = 12px → 落在下限，结果 12px
  • 视口 450px：4vw = 18px → 落在区间内，结果 18px
  • 视口 700px：4vw = 28px → 超过上限，结果 24px

为什么用 clamp 而不是 calc？ calc(4vw) 只会给出一个可能过大或过小的值；clamp 让它在小屏和大屏分别被 MIN/MAX 兜住，中间连续插值。它不是某种"智能响应"，就是取 min 和 max 组合出的夹逼。

写数值要自洽：同一段推算里，根字号写成 16px，就别在算式里按 10px 算；一个例子说视口 450px，4vw 就必须是 18px。参照物、数字、结果三者要能对上。

再举一个混用 rem 的例子：clamp(1rem, 4vw, 2rem) 在根字号 16px 时等价于 clamp(16px, 4vw, 32px)；如果另一句里假设根字号是 10px，上下限就该是 10px 和 20px。写成 rem 不代表可以忽略它背后的像素值——参照物一变，整个夹逼区间都跟着变。

12 · 为什么动画会卡

一句话模型：属性改动会从"样式计算 → 布局 → 绘制 → 合成"中的某一站进入流水线，落得越靠前，后面重做的越多——width 从布局进、background-color 从绘制进，transform/opacity 在独立成层时只从合成进。

先看一个现象

两根绿条都在 1 秒里从 120px 变成视觉上的 300px：

css
.bar { width: 120px; height: 40px; background: #2f6f4f; transform-origin: left; }
@keyframes grow-width { to { width: 300px; } }
@keyframes grow-x     { to { transform: scaleX(2.5); } }
.grow-width { animation: grow-width 1s linear infinite; }
.grow-x     { animation: grow-x    1s linear infinite; }

120 × 2.5 = 300，两根条的终点重合，肉眼几乎分不出。你以为它们只是两种写法；实际打开 Performance 录制，第一根每帧都写着 Layout 和 Paint，第二根只有 Composite Layers。当页面上还有几十个元素、或者主线程正忙着处理点击时，第一根开始掉帧，第二根照常走。

差别不在"动不动"，而在于两行 CSS 把改动交给了流水线的不同站点。

还有一个让差别被放大的背景：60Hz 屏幕约每 16.7ms 出一帧，主线程要在这段时间里处理输入、算样式、布局和绘制，合成器再把结果送上屏。第一根把布局和绘制塞进每一帧的预算，赶上复杂页面就超时；第二根几乎不占主线程时间，自然稳。

先建立直觉

图里最关键的一条：流水线是单向依赖。布局决定画在哪，绘制决定画什么，合成决定怎么叠。因此从布局进的改动无法跳过后面两站；而从合成进的改动没有下游可连累，这就是它轻的全部原因。

这也是为什么"查表记住哪些属性会重排"不是好办法：表会随浏览器实现变化，而流水线的依赖方向不变。你要判断的是一个改动让哪一站的产物失效，不是某个属性的名字。

机制拆成四步

1. 四站各回答一个问题

样式计算回答"每个元素最终用哪个值"，布局回答"每个盒子多大、放在哪"，绘制回答"把这些盒子画成哪些像素指令"，合成回答"按层叠顺序把各层叠成最终画面"。

把开头的绿条走一遍就清楚了：样式阶段算出 width 此刻是 180px；布局阶段据此定出盒子的宽高和起点；绘制阶段生成"左边这条 40px 高的绿色矩形"的指令；合成阶段把它所在的层叠上去。等 width 变成 181px，前两站的结论都过期了，只能重算。

为什么必须先分清这四站？ 因为每一站的输入就是上一站的输出。改动 width 让盒子变宽，依赖它的换行、兄弟位置、需要绘制的区域全部失效；改动 background-color 时盒子几何没变，布局的结果仍然有效，可以跳过；改动 transform 时连像素都没重新生成，只是把画好的层整体做一次几何变换。把"失效的范围"想清楚，后面两站做不做就自动推出了。

注意：任何属性变化都会重新算样式，这一步几乎省不掉；真正拉开差距的是后面三站。所以"只走合成"说的是跳过布局和绘制，不是零成本。

2. 判断方法：连问三个问题

不用背优化清单，对每个会变的属性依次问：

提问命中就从这一站进入典型属性
会改变盒子在文档流里的尺寸或位置吗？布局（连带绘制、合成）width height margin padding font-size left top
不改几何，但改变"画出来长什么样"吗？绘制（连带合成）background-color color box-shadow border-color
只改整体的位移、缩放、旋转、透明度吗？合成（前提：独立成层）transform opacity

为什么第一问优先？ 改几何会同时改写布局的产物，而后两站消费的正是这份产物，所以只能从布局重跑。

为什么第二问能跳过布局？ 元素仍占同样大小、同样位置，只是颜色或阴影不同，布局阶段算出的坐标可以原样复用。

为什么第三问有个前提？ transform 和 opacity 描述的是"整层怎么摆""整层多透明"，不需要知道内部盒子多大。但只有元素拥有自己的合成层时，浏览器才能把这份变换交给合成器独立完成；如果它和别人的内容共用一层，浏览器仍得把这一层重新绘制一次。所以"只走合成"是条件结论，不是属性保证——transform 并不永远不触发绘制。

拿两个常见属性走一遍：改 font-size 会改变文字占据的行高，第一问命中，落到布局；改 border-color 不改任何尺寸，第二问命中，落到绘制。注意第一问只要命中一次就停止，不必再问后面两问——下游会被连带重做，答案是确定的。

3. transform 不改布局盒，却会改掉后代的包含块

这是最容易说错的地方。给元素 transform: translateX(100px)：

  • 它自身的布局盒没变：offsetWidth 不变，它在文档流里占的那块空间也没变，兄弟元素不会挪过来。getBoundingClientRect() 会返回变换后的视觉位置，但那不是布局盒的尺寸。
  • 它同时成为 position: fixed 和 position: absolute 后代的包含块，并建立层叠上下文。后果很具体：
css
.panel { transform: translateX(0); }        /* 非 none 即可，0 也算 */
.pin   { position: fixed; top: 0; right: 0; }
.cover { position: absolute; inset: 0; }    /* inset 是四边的简写 */

.pin 本该贴视口右上角，现在改为相对 .panel 定位，会跟着 .panel 移动和滚动；.cover 也不再填最近的定位祖先，而是填 .panel 的内边距盒。

所以准确的说法是"transform 不改变元素的布局盒尺寸与流中占位"，而不是"transform 对布局没有影响"。它换了后代的参照系，这属于布局语义，却不需要重新排版兄弟元素——两件事并不矛盾。

反例能帮你把边界划清：opacity: 0.5 也会建立层叠上下文，但不会成为包含块，后代的 fixed/absolute 参照不变；will-change: transform 则因为规范要求在真正设置 transform 前就建立相同的上下文，所以同样会改参照系。层叠上下文管"谁画在前面"，包含块管"偏移量从哪算"，两者常被同一批属性触发，却是不同的事。

4. 两个把"卡"放大的机制

强制同步布局（布局抖动）：浏览器平时把样式改动攒着，到该出帧时一次算完。但如果你先写样式、紧接着读一个依赖布局的值——offsetWidth、getBoundingClientRect()、scrollTop、getComputedStyle() 的几何值——浏览器必须立刻把攒着的布局算出来才能给你准确数字。这一读就把流水线强行拉回布局站。

js
for (const box of boxes) {
  box.style.width = '300px';   // 写：让布局失效
  total += box.offsetWidth;    // 读：强制立刻布局一次
}

为什么会抖？ 循环里每次读都逼浏览器把上一次写的布局结算掉，于是 N 个元素就是 N 次同步布局，而不是攒成一次。判断方法很简单：读几何值就是同步点，把读集中到写之前，或用 requestAnimationFrame 把写集中到下一帧。

CLS（累积布局偏移）：衡量视觉稳定性的指标，累计可见元素在帧之间发生的非预期起始位置移动。常见来源是没写尺寸的图片、晚到的字体、页面顶部后插入的横幅。

为什么它属于这一篇？ 因为偏移的本质就是布局位置变了：改 width、top、margin 的动画会改元素的布局位置，可能计偏移；基于 transform 的合成动画只动视觉层、不推动任何其他元素，因此不计入 CLS——即使被移动的元素已经在自己的层上，改 top/left 仍会产生布局偏移。注意边界：用户输入后 500ms 内的偏移带 hadRecentInput 标记，会被排除。

容易误判的地方

  • "transform 永远不重绘" → 只有元素在独立合成层上才可能只合成；和别人共层时仍要重绘。同理，opacity 的"合成-only"也有这个前提。
  • "will-change: transform 会强制开一层，所以随便加" → 它是提示，浏览器可以忽视；每层都占显存，滥用反而更慢。而且按规范，只要非初始值会建立层叠上下文/包含块，will-change 命名该属性时也必须建立——它会改后代的定位参照，不是无副作用的开关。
  • "contain 能让重排消失" → contain: layout/paint 只是把影响范围关进子树，代价是元素成为后代的包含块、建立层叠上下文，paint 还会裁切溢出；contain: size 更会让元素不再由内容撑开，必须自己给尺寸。
