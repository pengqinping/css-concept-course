# 26 · 谁真的缩小了范围

> **前置**：会按第 02 篇从右端锚点向左验证一条后代选择器；会按第 03 篇的四元组 `(行内, ID, 类/属性/伪类, 标签/伪元素)` 与层叠关卡判断谁胜出；知道自定义属性会继承（第 04 篇），因此它不因任何 DOM 边界而自动断开。
>
> 上一篇：[变化如何发生](25-rendering.md) ｜ [本阶段目录](README.md)

## 1. 本章目标

- 给定一段原生嵌套，能把它手工展开成扁平选择器，并说出它的优先级与手写形式是否相同。
- 给定 `@scope (.card) to (figure)`，能说出哪些元素参与匹配、哪些继承属性仍越过下限，并解释"近根者胜"在层叠里的位置。
- 给定 `.card:has(button:disabled)`，能指出被选中的是谁、匹配方向从哪里出发，以及 DOM 有没有变化。
- 面对"样式只作用于本组件"的需求，能分清该用嵌套、`@scope` 还是 `:has()`，并说出各自没能做到什么。

**为什么现在学这个**：第 23 篇用命名和令牌约束影响范围，但那都是"写出来的边界"。这一篇检验三种看起来像"局部化"的新语法——嵌套、`@scope`、`:has()`——到底哪一种是真的边界。把它们混成一回事，是维护阶段最隐蔽的踩坑来源。

## 2. 新增模型

先看三行看起来都在做"局部化"的代码：

```css
.card { & button { color: red; } }
@scope (.card) { button { color: blue; } }
.card:has(button:disabled) { opacity: 0.6; }
```

你以为第一行把规则收进了 `.card`、第二行把范围锁进子树、第三行根据内部状态选中卡片。实际：`& button` 编译成 `.card button`，嵌进来的第三方按钮一起变红；`@scope` 只限制"哪些元素参与匹配"，卡片里继承来的 `font-family` 照样穿过边界；`:has()` 连 DOM 都没碰，只是让 `.card` 因为后代的状态被选中了。

三个"局部感"来自三个完全不同的轴：**书写组织、影响范围、匹配方向**。

**模型：嵌套只改书写方式，`@scope` 才给样式一个 DOM 子树边界并加邻近性排序，`:has()` 只把匹配方向反过来；三者都不改 DOM，也都不免掉第 03 篇的层叠关卡。**

![`:has()` 把匹配的箭头掉了个头](figures/26-scope-nesting.svg)

*图 26-1 · `:has()` 把匹配的箭头掉了个头*

图是同一棵小 DOM 树画两遍。左半：`@scope` 圈出一个"甜甜圈"——根 `.card` 包含在内，下限 `figure` 及其子树被排除；一条虚线从根绕过下限，标注"继承属性照穿"。右半：`.card:has(button:disabled)` 的匹配箭头从内部 `button:disabled` 出发，反向指回外层 `.card`；节点、连线、顺序一模一样，只有箭头方向反了。

**这张图的一句话结论：作用域限的是"谁参与匹配"，方向换的是"谁被选中"，两者都不隔离样式、都不改 DOM。**

术语落地：

- **原生嵌套**：在一条规则里写子规则，`&` 指向外层选择器本身；编译后仍是扁平选择器。
- **`@scope`**：给一组规则画出 DOM 子树边界；根到下名为"甜甜圈"，下限之外排除匹配。
- **邻近性（proximity）**：多个 scope 冲突时，离根更近的规则胜出，是层叠的最后一步。
- **`:has()`**：相对选择器函数，用后代状态反向命中外层容器。

## 4. 原理与规则

### 4.1 原生嵌套：语法糖，不是作用域

`&` 指向外层选择器本身，可放在链首、链尾或中间：

```css
.card {
  &:hover { border-color: #3157d5; }      /* .card:hover */
  & .title { font-weight: 700; }          /* .card .title */
  .theme-dark & { background: #171a21; }  /* .theme-dark .card */
}
```

不写 `&` 的子规则会自动补成后代选择器：

```css
.card {
  & > h2 { margin-block: 0; }    /* .card > h2 */
  a { color: #2548bd; }          /* .card a */
}
```

**为什么它不算作用域？** 浏览器最终存的还是扁平选择器，和手写的 `.card button` 没有区别；第 03 篇那串关卡——来源、重要性、层、优先级、书写顺序——一条都没少。嵌套后的优先级类似 `:is()`：取参数里最高的一项，不会因为套了三层就自动"组件隔离"。

**失效条件**：`.card { & .title {} }` 与 `.card .title` 优先级完全相同，前者只是写在更近的位置；当第三方按钮嵌进 `.card` 时，`.card button` 照样命中它——嵌套没有提供任何隔离。

### 4.2 @scope：限定参与匹配的子树，再加邻近性

```css
@scope (.article) to (figure) {
  img { border: 2px solid #16805a; }
}
```

根（`.article`）包含在内，下限（`figure`）及其子树被排除，形成甜甜圈。同一个 scope 里的写法：

```css
@scope (.theme) {
  :scope { padding: 1rem; }     /* 指 .theme 本身，带类级优先级 */
  & a { color: #2548bd; }       /* .theme a */
  p { line-height: 1.6; }       /* 裸选择器 ≈ :where(:scope) p */
}
```

`:scope` 指根本身；不带 `&` 的裸选择器相当于前面隐式加了零优先级的 `:where(:scope)`。**为什么要区分？** 显式写 `:scope` 引入一个类级优先级位，裸选择器不增加优先级——想让后续普通类轻松覆盖就用裸选择器，要锁定根节点本身才写 `:scope`。

还有一层排序：同一属性在多个 scope 里冲突时，离根更近的胜出，比如 `.light` 里套 `.dark` 再套 `.light`，最深的 `.light` 赢。**为什么它排在这一步？** 这正是第 03 篇最后那一步"作用域距离"，它只在来源、重要性、层、优先级都打平后才起作用。

**失效条件**：scope 不是沙箱。继承属性（`color`、`font-family`）仍越过下限影响子树外部；它也不能用 `:scope + p` 去选外面的兄弟。默认样式表里没有 `:scope` 的优先级加成，用裸选择器写 `:where(:scope) p` 的优先级需要单独核对。

### 4.3 :has()：用后代状态反向选父级

```css
.field:has(input:invalid) label { color: #a53d2b; }
```

普通选择器从右端锚点往左验证（第 02 篇）；`:has()` 把锚点换成括号内的 `input:invalid`，命中后再回到外面的 `.field`。括号里仍是相对选择器，可继续用 `>`、`+`、`:nth-child()` 描述内部关系。

**为什么它解决"状态驱动"？** 以前要让父级知道内部状态得用 JS 加类名；现在选择器自己就能表达"含有无效输入的那个表单项"，DOM 不动，JS 可省掉。

它的优先级取括号内参数最高的一项（和 `:is()` 同规则）。`.field:has(input:invalid) label` 是 `(0,0,2,2)`，`.field label` 是 `(0,0,1,1)`，前者更高。代价是可审查性：能用一个状态类说清时，不必为了少写一行类把条件全塞进 `:has()`。

**失效条件**：`:has()` 中整条选择器列表里的参数不参与锚点定位，只做条件判断；把需要命中的关键元素只挂在一个复杂的 `:has()` 条件上时，表达式越复杂越难一眼看出选中了谁，且不支持该特性的环境里规则整条丢弃。

### 4.4 三者各管一件事

| 你想解决的问题 | 用哪个 | 它不改变什么 |
| --- | --- | --- |
| 组件规则写在一起、少重复类名 | 原生嵌套 | 扁平选择器与优先级照旧 |
| 限制样式能在哪棵子树里匹配 | `@scope` | 不阻断继承，不提高优先级 |
| 根据后代状态选中外层容器 | `:has()` | 不改 DOM，不改匹配方向以外的东西 |

**为什么必须分开记？** 它们的失败方式不同：嵌套失败在"以为局部、其实全局命中"，scope 失败在"以为隔离、其实继承照穿"，`:has()` 失败在"以为改了结构、其实只是选中了别的元素"。把三者当成同一件事，调试时就会找错方向。

回退也要分别看：原生嵌套交给构建链展开；`@scope` 不支持时基础选择器仍要独立给出可读样式；`:has()` 不支持时用 JS 补一个状态类，别把关键信息只挂在 `:has()` 上。

**失效条件**：三者叠加不会让边界更硬——继承照穿、优先级照算。用嵌套把规则写在一起、用 `@scope` 画边界、用 `:has()` 表达状态，只是书写和表达更清楚，不是三层安全锁。

## 5. 常见坑

**坑 1：以为嵌套让样式局部化**
- **原因**：它只是把规则写在一起，编译后仍是 `.card button` 这样的扁平选择器，命中所有后代。
- **确认**：展开选择器后在 DevTools 的 Matched Rules 里数命中元素，看第三方按钮是否也在列表里。
- **修法**：真要限定范围就配合 `@scope` 或用构建期哈希类名（第 23 篇）；代价是需要额外工具或新语法回退。

**坑 2：以为 @scope 是样式沙箱**
- **原因**：它只限定参与匹配的子树并加邻近性排序；继承属性照穿，优先级规则照算。
- **确认**：在下限 `figure` 内放一个无自身 `font-family` 的段落，看它是否仍从根继承到字体。
- **修法**：要断继承就显式在子树上重置属性值，或改用 Shadow DOM（第 30 篇）；代价是要重新处理焦点与主题穿透。

**坑 3：以为 :has() 会改 DOM 或绕过优先级**
- **原因**：DOM 一动不动，优先级仍取括号内参数最高的一项。
- **确认**：切 `:has()` 规则前后用 demo 的 `DOM 元素总数（实测）` 对比，再把 `.field label` 与 `.field:has(input:invalid) label` 的特异性算一遍。
- **修法**：按 `(行内, ID, 类/属性/伪类, 标签/伪元素)` 写清优先级，把状态类作为兼容回退；代价是维护两份表达。

## 6. 练习

1. **基础**：把 `.card { & button { padding: 0.5rem } }` 手工展开，用 DevTools 的 Matched Rules 核对。
   验收：展开为 `.card button`，特异性 `(0,0,1,1)`，与手写规则完全一致；卡片内第三方按钮同样命中。

2. **基础**：写 `@scope (.card) to (figure) { p { color: red } }`，在 `figure` 内放一个带自身 `font-family` 的段落。
   验收：figure 内的 `p` 不被这条命中（保持原色），但它从 `.card` 继承来的 `font-family` 仍生效——证明 scope 不阻断继承。

3. **进阶**：写 `.field:has(input:invalid) label { color: red }` 与 `.field label { color: blue }`，切换 input 的有效性。
   验收：输入无效时 label 为红色、恢复有效时为蓝色；两条规则特异性分别为 `(0,0,2,2)` 与 `(0,0,1,1)`，红色胜出且与源码顺序无关，DOM 节点数前后相同。

4. **进阶**：在同一元素上写两个 scope，`.light` 里套 `.dark` 再套 `.light`，各自给 `--tone` 不同值。
   验收：最深的 `.light` 的值胜出，因为它跨越的 DOM 层级最少；把来源、层、优先级都打平后，邻近性才成为判据。

5. **挑战**：不查资料，预测 `@scope (.card) { :scope { color: red } p { color: blue } }` 里 `:scope` 与裸选择器 `p` 各自贡献的优先级，再用浏览器核对。
   验收：`:scope` 带一个类级优先级位 `(0,0,1,0)`，裸选择器 `p` 相当于 `:where(:scope) p`，只有标签级 `(0,0,0,1)`；在两者都可能命中的元素上，`:scope` 的规则胜出。
